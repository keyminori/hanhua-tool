# 汉化工具 · 通用版

把一套"给某个游戏定制的机翻脚本"重做成**谁都能拿来翻自己游戏**的工具。
核心能力：批量机翻日文文本表 → 产出中文表，带**术语硬约束**、**多项目管理**、
**网页工作台**、**百度账号池**、**调速**，可以打包成 exe 双击运行。

---

## 一、一分钟上手

1. 双击 `汉化工具.exe`（或 `hanhua.py`）→ 控制台菜单
2. 按 `4` 建项目：填**日文源目录**（放着待翻的 `.txt` 表）和**中文产物目录**
3. 按 `1` 开网页工作台，浏览器自动打开 `http://127.0.0.1:8777`
4. 在工作台 ① 术语表里加几条固定译法
5. 回到控制台按 `2`（或在网页里点"启动引擎"）开始翻译

源表的格式（每行一条，TAB 分隔，可用工作台改列号）：

```
001<TAB>初陣の直後に、蒼炎騎士団の<br>案内役を命じられるなんて！<TAB>VO_xxx
```

产物保持**同样的行数、同样的行号、同样的第三列**（语音 cue 之类），只把第二列换成中文。

## 二、设计思路

这套东西是从《为谁炼金》的汉化脚本里长出来的，下面每一条都是**踩过坑才定下来的**，
不是拍脑袋的架构洁癖。

### 1. 代码和数据彻底分开（本工具最重要的一个决定）

老版本所有状态文件（术语表、缓存、敏感句、账号、调速）都堆在代码目录旁边，
换一个游戏就得改源码里的路径常量 —— 等于不能给别人用。

现在：

```
工具目录/                （代码，只读也行）
    core/  ui/  hanhua.py
数据目录/                （默认 工具目录/projects，装到 Program Files 时自动退回用户目录）
    _common/accounts.json        ← 账号跨项目共享，别每个项目配一遍
    <项目名>/
        project.json             ← 源目录 / 产物目录 / 文件匹配 / 列号
        glossary.json            ← 术语表
        tm.json                  ← 引擎实际读的术语表（由术语表生成，别手改）
        sensitive.json           ← 敏感隔离句
        manual_ov.json           ← 人工改稿台账
        engine_cfg.json          ← 调速
        mt_cache.json            ← 翻译缓存
        _run.log                 ← 引擎日志
```

切换项目 = 换一份 `project.json`。引擎里那些路径是**模块级常量**，Python 函数运行时
现查 globals，所以 `mt.set_home(工作区)` 改一次字典就能整体搬家 —— 引擎内部一行都没动。

### 2. 术语表是硬约束，不是"建议"

机翻最烦的不是翻错，是**同一个名字前后翻得不一样**（蕾布娜 / 雷布娜 / 蕾芙娜）。

做法：送翻之前把日文专名换成占位符 `ZQX###QXZ`，翻完再换回你指定的中文。
引擎从头到尾没见过这个词的日文，也就没机会自由发挥。所以术语表**一定生效**。

配套两个机制：

- **占位符会被引擎改写**（实测 `ZQX224QXZ` → `PZQ224QXZ`，还可能夹空格），
  所以还原时按中间的数字找回，不是傻傻做字符串替换。
- **改了术语，翻完的行不会自己变**。译文一旦落盘，"已有中文就保留"的闸门会挡住重翻。
  所以改术语必须**回溯**：把受影响的行的译文退回日文原文，引擎下一轮用新译名重翻。
  工作台的「回溯重翻」按钮就干这个，命令行是 `hanhua.py term retro`。

### 3. 超时只看字符数，不看行数 —— 红线装在加载侧

百度大模型通道实测：677 字符 2.4 秒返回；1056 字符起**每次精确 25 秒整超时**（客户端超时，
服务端根本没回）。而默认的单请求上限是 3000 字符，正好落在死区。

于是加了一张红线表，并且**夹紧写在配置加载的地方**（`norm_run_cfg`），不是保存的地方：

```python
ENGINE_CHAR_CAP = {'baidu_llm': 800, 'baidu': 6000}
```

这样无论从网页滑块改、`hanhua.py cfg` 改、还是**手改 `engine_cfg.json`**，都会被夹住。
护栏装在保存侧的话，手改文件就绕过去了 —— 那条路一定会有人走。

### 4. 进度卡住的元凶是"死循环"，不是"翻不动"

现象：日志每轮 `api=0, cache=484`，进度永远差一点点。

真因：`collect` 判定"产物里还有假名 → 需翻"，但缓存里存的就是那份**带日文残留的译文**，
写回原样 → 下一轮再判需翻 → 无限空转。修掉的是两件事：

- **中文间隔号「・」(U+30FB) 被当成日文假名**：`魔炎将军卡伊扎尔…三杰・最后的一人`
  这种翻好了的行永远判需翻（723 行里 141 行纯属误判）。
- `os.replace` 在 Windows 上偶发 `WinError 5`（目标被索引/杀软短暂占用），
  一炸整轮白写 → 加重试。

判定改对之后，剩下的真残留用**换通道**解决（见下）。

### 5. 两条通道互补，重翻只许变好不许变差

大模型翻不动的短句、拟声词，通用翻译通道反而能啃下来。所以工具里留了
「换一条通道重翻残留行」的能力，并且带**安全阀**：

> 只在新译文的假名残留比旧译文**更少**时才采用。

所以无论跑多少次，结果只会变好，不会被差的译文覆盖。

### 6. 账号要体检，而且要用真载荷体检

早先的"体检"发一句「こんにちは」—— 5 个字符，234ms 全绿。后来证明它**零预测力**：
短请求压根不进模型也不占额度，测出来全绿，实际大载荷必超时。**这是个假绿灯**，
现在体检发 20 行真实日文（约 700 字符）。

账号状态（`accounts.json`）是**热生效**的：改完 1 秒内生效，不用重启引擎。
三层闸：轮转时跳过 → 单账号调用前复查 → 装池时复用实例但同步密钥。

### 7. 不要弹黑窗

后台进程用 `pythonw` 拉起时，它跑任何子进程都会**新建一个控制台窗口**。
所以工具里所有 `subprocess` 都带 `CREATE_NO_WINDOW (0x08000000)`。

### 8. 单一真源

数值只在引擎里有一份：术语表 → `tm.json` 由脚本生成，界面显示的值 = 真正生效的值
（`run_cfg_defaults` 也要过红线，否则界面显示"默认 3000"、实际生效 800，就是在骗人）。

## 三、目录结构

```
hanhua/
  README.md              本文件
  hanhua.py              统一入口（双击/命令行都走它）
  启动.bat               双击启动控制台
  core/
    mt.py                翻译引擎（账号池/掩码/缓存/术语/后处理/调速）
    mt_story.py          批量收集与写回（含行数、cue 闸门）
    project.py           项目管理（多工作区）
    glossary.py          术语表 + 回溯
    runner.py            翻译主循环（一轮 20000 行，翻完写回）
    manual.py            改稿/查行
    sens_mt.py           隔离句机翻通道
  ui/
    server.py            网页服务（总览 / 实时窗口 / 工作台）
    page.html            工作台页面
  projects/              项目数据（备份就拷这个目录；exe 也用这一份）
  汉化工具.exe           打包后的独立程序（双击即用）
  build/                 打包脚本
```

## 四、使用说明

### 三种用法（同一份实现）

| 方式 | 怎么开 | 适合 |
|---|---|---|
| 网页工作台 | `hanhua.py gui` 或控制台 `1` | 日常用，所有功能都在里面 |
| 控制台菜单 | `hanhua.py` 双击 exe | 不想记命令 |
| 命令行 | `hanhua.py <子命令>` | 批量/脚本化 |

端口默认 8777；被占用会自动往后挪（实际端口写在 `_port.txt`，启动时也会打印）。

### 网页工作台

- `/` 进度总览：总量、已译、剩余、速度
- `/live` 实时窗口：一条条看正在翻什么
- `/manual` 工作台：六张卡
  - **⓪ 项目**：切项目、新建、设日文源/产物目录（有目录选择器）、文件匹配、列号
  - **① 术语表**：增删改、批量导入 CSV、改完一键回溯重翻
  - **② 引擎调速**：通道/并发/批次/频率，改完热生效
  - **③ 百度账号**：逐个停用、新增、体检
  - **④ 找行 · 改译文**：按关键字或 `文件#行号` 定位，直接改（登记台账，引擎不会覆盖）
  - **⑤ 手动请求台**：任意日文指定通道各发一次，对比译文
  - **⑥ 已改稿台账**：看改过哪些行，可还原

### 命令行

```bash
hanhua.py project list                       # 看有哪些项目
hanhua.py project new 游戏名 J:\游戏\日文 [产物目录]
hanhua.py project switch 游戏名
hanhua.py project set src_dir J:\别的目录
hanhua.py project set cols 0,1,2             # 列号（没有 cue 列就填 -1）
hanhua.py project set sep \t

hanhua.py term list                          # 术语表
hanhua.py term set アルケミスト 炼金术师 职业名
hanhua.py term del アルケミスト
hanhua.py term retro                         # 改完术语必跑：退回受影响的行重翻

hanhua.py run                                # 前台翻译（Ctrl+C 停）
hanhua.py run --detach                       # 后台翻译
hanhua.py status                             # 进度
hanhua.py acc list / off llm 969 / add <appid> <key> llm / test llm 969
hanhua.py cfg view / workers 6 / batch_chars 700 / engine baidu_llm
```

### 打包成 exe

```bash
hanhua.py build          # 或 build\打包.bat
```
产物会**自动挪到工具根目录**：`汉化工具.exe`（约 10 MB，只依赖系统自带的东西）。
双击它 → 控制台菜单。拷到别的电脑只要带这一个 exe 就行，项目数据建在 exe 旁边
（装到 Program Files 时自动退回 `%LOCALAPPDATA%\HanhuaTool`）。

> 放在根目录而不是 `dist/` 里，是因为**数据目录 = exe 所在目录/projects**。
> 万一 exe 被挪进了某个子目录（比如你自己拷进 `dist/`），它会先看同层的
> `projects/` 里有没有真项目目录，没有就**往上一层找**——不会盯着空壳
> 给你一个"还没有项目"的假象。（判据：`projects/` 下除 `_common` 外至少有一个项目目录）

## 五、接一个新游戏

1. 拿到日文文本表（TAB 分隔：`行号<TAB>原文<TAB>可选cue`），放一个目录
2. 控制台 `4` → 新建项目 → 填这个目录；产物目录留空就用默认
3. 如果只翻部分文件：
   - `文件匹配`（如 `story_*.txt`）按通配符挑文件
   - 或者填 **`只翻哪些文件（正则）`**（`file_re`），例如 `^(qe|eq_|cq_)|_a_2d`
     只翻剧情文件、跳过 UI 文本和道具名。**大小写不敏感**，不用管文件名大小写。
     留空 = 目录里的表全翻
4. 如果表格式不同：设 `列号` 和 `分隔符`（csv 就把 sep 设成 `,`）
5. 加术语：角色名、地名、专有名词先钉死，能省掉后面大量手改
6. 开翻

## 六、常见问题

**Q：进度一直是 100% 但没在翻？**
看 `_run.log`：如果每轮都是 `api=0` 且 `cache=N`，就是"译文不合格但缓存命中"的死循环。
先确认术语表改过没有（改了要 `term retro`），再检查是不是间隔号「・」之类的假名判定问题。

**Q：换了个游戏，翻出来全是乱码/空行？**
多半是列号不对。用 `hanhua.py project set cols 0,1,2` 试试，或者打开源表确认分隔符。

**Q：翻译很慢？**
- 并发调大：`hanhua.py cfg workers 6`
- 请求间隔调小：`hanhua.py cfg sleep_ms 0`
- 账号不够用：`hanhua.py acc list` 看可用数，停用掉的号可以试着启用回来
- 想换通道：`hanhua.py cfg engine baidu`（通用通道快）；想用大模型就
  `hanhua.py cfg engine baidu_llm batch_chars 700`（**700 必须带上**，不带必超时）

**Q：同一个词前后译名不一致？**
加进术语表，然后 `hanhua.py term retro`。机翻不会记得上一行翻过什么，
只有术语表能保证全项目统一。

**Q：会覆盖我手改过的译文吗？**
不会。手改过的行进 `manual_ov.json` 台账，引擎写回时台账优先级最高。
要还原就在工作台 ⑥ 台账里删掉那一条。

**Q：exe 在别的电脑上跑不起来？**
整个 `dist` 目录一起拷（里面有依赖）。首次运行联网即可（翻译要调百度/谷歌接口）。

## 七、和《为谁炼金》专用版的关系

这工具是从那套脚本抽出来的：`core/mt.py`、`mt_story.py`、`sens_mt.py` 就是原来的引擎，
只改了"路径可注入、文件名过滤可配、列格式可配"这三件事，翻译逻辑、术语保护、
敏感词隔离、账号池、调速全都保留。

老项目（`J:\tagatame`）不受影响，继续用原来的面板和计划任务。
想把它接进新工具，就新建一个项目指到它的目录：

```bash
hanhua.py project new 为谁炼金 J:\tagatame\解包\_extract\剧情文档\Loc\japanese J:\tagatame\解包\汉化\chinese
```
